# Обработчик UMUX-Lite

Docker-first пайплайн на Python принимает одну или несколько CSV-выгрузок UMUX-Lite, нормализует и валидирует данные, разрешает дубликаты идентификаторов ответов, рассчитывает оценки UMUX-Lite и создаёт проверяемые CSV/JSON-артефакты и автономный интерактивный HTML-дашборд. Он параметризован схемой и TOML-конфигурацией, а не привязан к прилагаемому примеру.

На хосте нужен только Docker. Python и все зависимости Python запускаются внутри контейнеров.

## Предварительные требования

- Docker Engine (или Docker Desktop, использующий Docker Engine);
- Docker Compose v2, доступный как `docker compose`.

Проверьте установку из корня репозитория:

```text
docker --version
docker compose version
```

Локальное виртуальное окружение Python, установка пакетов или выполнение Python на хосте не требуются.

## Быстрый старт

Соберите образы, запустите полный набор тестов и обработайте прилагаемый пример:

```powershell
docker compose build pipeline tests
docker compose run --rm tests
docker compose run --rm pipeline `
  --input /input/data.csv `
  --output /output `
  --config /app/config/normalization.toml
```

Последняя команда запишет артефакты в `./output` на хосте. Откройте `output/dashboard.html` непосредственно в браузере: файл автономен и не требует веб-сервера.

### Полезные команды Docker

| Команда | Назначение |
| --- | --- |
| `docker compose build pipeline tests` | Собрать production-образ CLI и тестовый образ. |
| `docker compose build` | Собрать образы всех Compose-сервисов, включая определение необязательного `api`. |
| `docker compose build --no-cache pipeline tests` | Чистая пересборка, если есть подозрение на кэш зависимостей или слоёв Docker. |
| `docker compose run --rm tests` | Запустить все модульные и интеграционные тесты в тестовом образе. |
| `docker compose run --rm pipeline --help` | Показать справку CLI без Python на хосте. |
| `docker compose config` | Вывести итоговую конфигурацию Compose; полезно для проверки bind-монтирований и переопределений окружения. |

Если сборка падает после обновления базового образа или зависимостей, повторите чистую пересборку. Если Docker не подключается к daemon, запустите Docker Desktop или Docker Engine и проверьте, что текущий пользователь может выполнять `docker`. Если артефакты не появились там, где ожидалось, выполните `docker compose config` и проверьте `UMUX_OUTPUT_DIR`: контейнер всегда пишет в `/output`.

## Запуск CLI

CLI принимает один или несколько путей к CSV либо glob-шаблонов и требует каталог вывода:

```text
umux-process [--config CONFIG] --input PATH_OR_GLOB [PATH_OR_GLOB ...] --output DIRECTORY [--verbose]
```

Во всех Compose-командах используйте пути контейнера:

```powershell
# Один файл
docker compose run --rm pipeline `
  --input /input/data.csv `
  --output /output `
  --config /app/config/normalization.toml

# Несколько файлов и glob. Кавычки сохраняют glob для CLI.
docker compose run --rm pipeline `
  --input /input/january.csv /input/february.csv '/input/exports/*.csv' `
  --output /output `
  --config /app/config/normalization.toml
```

В POSIX-оболочках используются те же пути контейнера:

```sh
docker compose run --rm pipeline \
  --input /input/data.csv \
  --output /output \
  --config /app/config/normalization.toml

docker compose run --rm pipeline \
  --input /input/january.csv /input/february.csv '/input/exports/*.csv' \
  --output /output \
  --config /app/config/normalization.toml
```

Совпадения glob-шаблона сортируются по разрешённому пути. Порядок аргументов ввода сохраняется, а файл, совпавший с несколькими шаблонами, читается только один раз. Имена генерируемых артефактов запрещены в качестве входов, чтобы результаты прошлого запуска не были случайно загружены повторно.

### Переопределение каталогов хоста

По умолчанию Compose монтирует корень репозитория в `/input` только для чтения, а `./output` — в `/output` для чтения и записи. Можно выбрать другие каталоги хоста без изменения `compose.yaml`.

PowerShell:

```powershell
$env:UMUX_INPUT_DIR = 'C:\exports'
$env:UMUX_OUTPUT_DIR = 'C:\umux-output'
docker compose run --rm pipeline `
  --input '/input/*.csv' `
  --output /output `
  --config /app/config/normalization.toml
```

POSIX-оболочка:

```sh
export UMUX_INPUT_DIR="$HOME/exports"
export UMUX_OUTPUT_DIR="$HOME/umux-output"
docker compose run --rm pipeline \
  --input '/input/*.csv' \
  --output /output \
  --config /app/config/normalization.toml
```

`/input` доступен в production-контейнере только для чтения. `/output` доступен для записи и является единственным местом, где сгенерированные артефакты сохраняются через настроенное bind-монтирование. Runtime-образ запускается от непривилегированного пользователя `app` (UID/GID 999). На Linux может понадобиться скорректировать владельца или права каталога вывода, чтобы этот пользователь мог записывать в bind mount. Docker Desktop обычно управляет этим сопоставлением в локальной разработке.

## Контракт входных данных и правила обработки

Каждый CSV должен содержать эти девять колонок. Дополнительные колонки сохраняются при загрузке с предупреждением, но не входят в схему обработки.

| Колонка | Обязательна | Правило |
| --- | :---: | --- |
| `response_id` | Да | Непустой идентификатор ответа. |
| `submitted_at` | Да | Точное соответствие формату времени из конфигурации; по умолчанию `%Y-%m-%d %H:%M:%S`; значение не может быть в будущем. |
| `product` | Да | Должен быть разрешён через явные алиасы продуктов из конфигурации. |
| `product_version` | Да | Непустая строка; значения вроде `2.0` остаются строками. |
| `platform` | Нет | Известные значения нормализуются к `Web`, `Android` или `iOS`; отсутствующее или неизвестное значение становится `Unknown`. |
| `country` | Нет | Допустимые двухбуквенные коды приводятся к верхнему регистру; отсутствующее или некорректное значение становится `Unknown`. |
| `user_segment` | Нет | Значения из конфигурации приводятся к каноническому регистру; отсутствующее или неизвестное значение становится `Unknown`. |
| `score1` | Да | Конечное целое число от 1 до 5; формы `3`, `3.0` и `3.00` допустимы. |
| `score2` | Да | Конечное целое число от 1 до 5; формы `3`, `3.0` и `3.00` допустимы. |

Все строковые поля обрезаются по краям до нормализации. Сопоставление продуктов нечувствительно к регистру после обрезки и использует только явные алиасы — нечёткое сопоставление отсутствует. Присутствующий продукт вне таблицы алиасов отклоняется с `unknown_product`; пустой продукт — с `missing_product`. Временные метки не содержат часового пояса и агрегируются по указанному календарному месяцу.

Все применимые построчные дефекты сохраняются как JSON-массив в `rejection_reasons`; валидация не прекращается на первой ошибке. Точные коды причин для оценок: `missing_score1`, `missing_score2`, `non_integer_score1`, `non_integer_score2`, `score1_out_of_range` и `score2_out_of_range`. Отсутствующая или некорректная временная метка получает `invalid_submitted_at`; дата позднее момента запуска очистки — `submitted_at_in_future`.

Отсутствующие обязательные колонки, пустой или повреждённый CSV, шаблон без совпадений и недоступная конфигурация являются ошибками файла/запуска, а не набором построчных отклонений.

### Политика обработки дубликатов

Записи группируются по нормализованному `response_id` после валидации и нормализации. Выбор детерминирован: порядок аргументов ввода, затем путь к исходному файлу, затем номер строки CSV.

1. Эквивалентные валидные копии: сохраняется первая детерминированная копия, каждая последующая валидная копия отклоняется с `duplicate_exact`.
2. Если валидные копии эквивалентны и тот же ID есть у невалидных копий, сохраняется одна валидная копия. Невалидные копии сохраняют исходные причины отклонения и получают `duplicate_context` = `duplicate_with_valid`.
3. Если несколько валидных копий имеют разные нормализованные полезные нагрузки анкеты, *все* валидные копии отклоняются с `duplicate_conflict`. Без приоритета источника или времени обновления пайплайн не выбирает победителя. Невалидные копии в этой группе ID сохраняют свои причины и получают `duplicate_context` = `duplicate_conflict`.
4. Если все копии невалидны, все строки остаются отклонёнными с исходными причинами и получают `duplicate_context` = `duplicate_all_invalid`.

`duplicate_context` — это метаданные аудита, а не дополнительная причина валидации для уже невалидной строки. Дубликаты и неразрешённые конфликты не участвуют в расчёте оценок и агрегатов.

### Метрика UMUX-Lite и доля отклонений

Оценка рассчитывается только для принятых анкет:

```text
umux_score = ((score1 - 1) + (score2 - 1)) / 8 × 100
```

Диапазон — от 0 до 100 включительно: `(1, 1)` даёт 0, `(3, 3)` — 50, `(5, 5)` — 100. Основная доля отклонений:

```text
отклонённые исходные строки / все загруженные исходные строки
```

В неё входят исключённые копии-дубликаты. Одна отклонённая строка может иметь несколько причин валидации, поэтому сумма счётчиков по причинам может быть больше числа отклонённых строк.

## Результаты

Каждый успешный запуск заменяет известные имена артефактов в каталоге вывода, а не дописывает данные. Пять аудит-артефактов сначала сериализуются во временные файлы рядом с итоговыми, затем заменяются; после этого генерируется HTML-отчёт. Сбой создания отчёта не удаляет готовые аудит-данные и, если возможно, создаёт короткое уведомление о недоступности дашборда.

| Артефакт | Назначение |
| --- | --- |
| `cleaned_responses.csv` | Принятые, нормализованные и оценённые анкеты с указанием исходного файла, строки и порядка входного аргумента. |
| `rejected_responses.csv` | Отклонённые записи с исходными значениями, lineage, JSON-массивом `rejection_reasons` и контекстом дубликата. |
| `monthly_aggregates.csv` | Число принятых ответов, среднее и медиана UMUX по календарному месяцу, продукту и версии; помесячная динамика есть только для соседних календарных месяцев. |
| `product_summary.csv` | Итоги по продукту: число ответов, общее среднее, среднее последнего месяца и изменение относительно предыдущего календарного месяца. |
| `quality_summary.json` | Глобальные числа исходных, принятых и отклонённых строк, число строк-дубликатов и счётчики причин отклонения. |
| `dashboard.html` | Автономный интерактивный дашборд со встроенными Plotly JavaScript и данными графиков. |

Дашборд содержит KPI-карточки (объём исходных данных, число принятых, доля отклонений и общее среднее), сравнение продуктов и версий по среднему UMUX за весь период (взвешенному по числу ответов), помесячные тренды с размером выборки, последние низкие комбинации, отрицательные помесячные изменения, причины отклонений и разбивку качества по продуктам. Он не задаёт универсальный порог «хорошего UMUX».

## Изменение конфигурации

В образ включена стандартная конфигурация [`config/normalization.toml`](config/normalization.toml). Безопасный порядок её изменения:

1. Скопируйте файл в версионируемое место, доступное через read-only монтирование `/input` (не размещайте его в каталоге генерируемых результатов).
2. Добавляйте только явные алиасы в `[products.aliases]` или `[user_segments.aliases]`; ключи алиасов обрезаются и case-fold нормализуются, поэтому не добавляйте два написания, сводящиеся к одному ключу.
3. Сохраняйте `[platforms].supported` непустым и без повторов. Несовпадающие platform и user segment нормализуются в `Unknown`, а не отклоняются.
4. Сохраняйте корректными `case` страны, длину кода, формат временной метки и порог отчёта. Конфигурация проверяется при запуске.
5. Выполните `docker compose run --rm tests`, затем репрезентативный Compose-запуск с `--config /app/config/normalization.toml`. Для собственной конфигурации поместите её под read-only монтирование `/input` и передайте путь вида `/input/...`.

Не используйте алиасы для неявного объединения потенциально разных продуктов. После каждого изменения алиасов просматривайте отклонённые записи, особенно строки с `unknown_product`.

## Коды завершения и логи

| Код | Значение |
| ---: | --- |
| 0 | Пайплайн завершён, в том числе если все строки отклонены и артефакты записаны. |
| 1 | Непредвиденная ошибка. |
| 2 | Некорректные аргументы CLI (стандартное поведение `argparse`). |
| 3 | Ошибка конфигурации, входа или данных, включая ошибки схемы и разрешения путей. |
| 4 | Невосстановимая ошибка записи результатов/артефактов. |

При успехе stdout завершается краткой сводкой сверки, например:

```text
Pipeline completed: raw=12 accepted=10 rejected=2 duplicates=1 output=/output
```

Этапные счётчики и пути к артефактам логируются в stderr. Построчные проблемы качества данных не прерывают запуск: они попадают в файл отклонённых записей. Для отладочных логов передайте `--verbose`.

## Архитектура и точка расширения

```text
Входные CSV
  → загрузка → очистка/валидация → дедупликация → расчёт оценки → агрегация
  → переиспользуемый сервис пайплайна → запись артефактов/дашборд
                                      ↗
                               CLI-адаптер сейчас
                               будущий HTTP-адаптер
```

`umux_processor.pipeline.run_pipeline_service(...)` — переиспользуемая граница оркестрации. CLI отвечает за разбор аргументов и сопоставление ошибок кодам завершения, а ядро пайплайна — за обработку от загрузки до аналитики. Будущий HTTP-адаптер должен вызывать тот же сервис, а не дублировать валидацию, расчёт оценок или агрегацию.

## Допущения и ограничения

- `submitted_at` не содержит часового пояса; группировка по месяцам использует указанное значение.
- Продукт и версия продукта — обязательные измерения агрегации. Необязательные platform, country и user segment не делают ответ невалидным.
- Дашборд предназначен для открытия локально без веб-сервера и показывает относительную эффективность, а не отраслевой порог.
- Помесячные изменения намеренно не вычисляются через пропущенные календарные месяцы.
- Известные CSV/JSON-артефакты заменяются независимо; при сбое ОС во время финальной замены теоретически возможен смешанный набор старых и новых файлов.
- Необязательный HTTP-эндпоинт из плана реализации не входит в поставляемый интерфейс репозитория.
- Исходные данные и результаты исключены из build context production-образа через `.dockerignore`; передавайте их через runtime bind mounts.
